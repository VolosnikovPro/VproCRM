# VproCRM v1.2 — Design

## Overview

Four independent improvements to the VproCRM codebase:

1. WebSocket push for Avito chat updates (replace frontend polling)
2. Split monolithic `app.js` into ES modules
3. In-memory API response cache
4. Overdue task notifications

---

## 1. WebSocket for Avito Chat Updates

### Problem

Frontend polls `/api/avito/chats` every 60 seconds via `setInterval`. The backend also syncs with Avito API every 60 seconds in a background thread. The frontend poll is redundant — data is already fresh on the backend.

### Solution

Add a FastAPI WebSocket endpoint. After each Avito sync cycle completes, the backend broadcasts a lightweight event to all connected WebSocket clients. The frontend connects once at page load and listens for push events.

### Architecture

- **Backend**: New endpoint `GET /ws/avito` (WebSocket). A `ConnectionManager` class tracks active connections. After `_sync_avito_chats()` runs, the manager broadcasts `{ type: "chats_updated" }` to all clients.
- **Frontend**: New module `avito.js` manages the WebSocket connection with auto-reconnect (3s, 5s, 10s backoff). On receiving `chats_updated`, it calls the existing `refreshAvitoChats()` function (no data payload — client re-fetches from REST).
- **No change** to backend Avito sync (remains setTimeout-based polling of Avito API).

### Why not push full data?

Minimal coupling. The event is just a signal. The client already has `refreshAvitoChats()` which fetches and renders. This avoids sending potentially large payloads over WebSocket and keeps the REST layer as the single source of truth.

### Files changed

- `server.py` — add WebSocket endpoint + ConnectionManager
- `static/app.js` (or new `avito.js`) — WebSocket client with reconnect

## 2. Split `app.js` into ES Modules

### Problem

`static/app.js` is 2800+ lines, all functions in global scope. Hard to navigate, maintain, or test in isolation.

### Solution

Split into ES modules served as static files. No bundler, no build step. Native `import/export` syntax.

### Module Structure

```
static/
├── index.html            # <script type="module" src="app.js">
├── style.css
├── app.js                # Entry: init, tab switching, settings, modals (re-exports from sub-modules)
├── utils.js              # api(), esc(), fmtMoney(), fmtDate(), declOfNum(), cache layer
├── pipeline.js           # renderPipeline(), createClientCard(), stage CRUD, search/filter, merge
├── tasks.js              # renderTasks(), renderCalendar(), toggleTask()
├── dashboard.js          # renderDashboard()
├── ads.js                # renderAdsPage(), refreshAds(), flat/grouped views, stats sync
├── avito.js              # Avito auth, chat polling → WebSocket client, message send
└── notifications.js      # Notification bell, feed, polling, overdue task check
```

### Migration Strategy

Phase 1 — extract independent utilities first:
1. Create `utils.js` (api, format helpers, cache) — no dependencies on other modules
2. Create `notifications.js` — depends only on `utils.js`
3. Create `ads.js` — depends only on `utils.js`

Phase 2 — extract UI modules:
4. Create `avito.js` — depends on `utils.js`, `notifications.js`
5. Create `pipeline.js` — largest module, depends on `utils.js`
6. Create `tasks.js`, `dashboard.js` — depend on `utils.js`

Phase 3 — slim down `app.js`:
7. `app.js` becomes entry point — imports everything, registers global callbacks (`window.switchTab`, etc.)
8. Remove all extracted functions from the old `app.js`

Each phase can be committed and tested independently.

### Global Function Strategy

The current code uses inline `onclick` handlers (`onclick="switchTab('pipeline')"`). ES modules don't pollute global scope. Solution: `app.js` explicitly assigns functions to `window` that HTML onclick attributes reference.

## 3. In-Memory API Cache

### Problem

Tab switches trigger duplicate API calls. `/api/stages`, `/api/sources`, `/api/tags` rarely change but are fetched on every render.

### Solution

A lightweight cache layer inside `api()` in `utils.js`.

### Design

```js
const _cache = new Map();  // key: url -> { data, ts }

function api(url, method = 'GET', body = null, options = {}) {
    const cacheKey = method + ':' + url;

    // GET with cache enabled
    if (method === 'GET' && options.cache !== false) {
        const hit = _cache.get(cacheKey);
        if (hit && (Date.now() - hit.ts) < (options.ttl || 30000)) {
            return Promise.resolve(hit.data);
        }
    }

    // Non-GET: invalidate all
    if (method !== 'GET') {
        _cache.clear();
    }

    // Fetch and cache
    return fetch(...).then(data => {
        if (method === 'GET') {
            _cache.set(cacheKey, { data, ts: Date.now() });
        }
        return data;
    });
}
```

### Cache TTL by endpoint

| URL pattern | TTL |
|---|---|
| `/api/stages`, `/api/sources`, `/api/tags` | 5 min |
| `/api/clients` | 30 s |
| `/api/dashboard` | 1 min |
| `/api/tasks`, `/api/calendar/*` | 30 s |
| `/api/avito/*` | 15 s (will be superseded by WebSocket) |

### Invalidation

- `POST`, `PUT`, `DELETE` → `_cache.clear()` (full invalidation, simple and safe)
- Optional: granular invalidation by key prefix for performance if needed later

## 4. Overdue Task Notifications

### Problem

No reminders for tasks with expired due dates. Avito and new-client notifications exist, but overdue tasks are invisible in the bell.

### Solution

Use the existing `Notification` model (`type = "overdue_task"`) and backend logic. The notifications endpoint already aggregates various types.

### Backend

In `server.py`, modify the notifications endpoint (or add a helper) to:

1. Query all tasks where `due_date < now AND completed == false`
2. For each, check if a notification `type="overdue_task"` with `link_id = task.client_id` already exists today
3. If not, create `Notification(type="overdue_task", message="Просрочена задача: {title}", link_id=client_id)`
4. Return combined notifications as before

### Deduplication

Check `WHERE type = 'overdue_task' AND created_at > today_start` — skip if already notified today. Prevents spam on every poll.

### Frontend

No changes needed. The notification bell already fetches `/api/notifications` and renders all types. Overdue tasks will appear automatically alongside Avito and new-client notifications.

### Client link

`link_id` = `client_id`. Clicking the notification in the frontend calls `openDetail(link_id)` which already works.

---

## Implementation Order

1. **Utils + Cache** — create `utils.js` with `api()`, cache layer, format helpers
2. **Notifications** — create `notifications.js` + backend overdue task logic
3. **WebSocket** — backend endpoint + frontend client in `avito.js`
4. **Module split** — extract `pipeline.js`, `ads.js`, `tasks.js`, `dashboard.js` one by one
5. **Slim `app.js`** — entry point, window globals, import all modules

---

## Rollout

No breaking changes. Each step is backwards-compatible:
- Old `app.js` functions remain accessible during migration
- WebSocket is additive — frontend falls back to polling if WS fails
- Cache is invisible to callers
- Overdue notifications just add new rows to existing table
